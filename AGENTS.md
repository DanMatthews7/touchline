# Touchline coding rules

- Read `GAME_SPEC.md`, `ARCHITECTURE.md`, `DATA_POLICY.md` and `ROADMAP.md` before changing behavior. On 20 October the user authorized Milestone 4's first career-management slice: contracts, wages, club budgets, calendar payments and financial history, with database research still deferred. Develop these in the isolated demo. Transfers, AI squad management, injuries, development, new seasons and 2D animation remain later slices. The real-data season still requires verified 2026/27 membership/current squads as of 16 October 2026 with dated sources and permitted use; do not call that integration complete.
- Keep simulation and domain code pure TypeScript, independent of React, browser APIs and persistence. Use explicit commands, deterministic state transitions and seeded randomness.
- Use strict types, validated boundaries and integer minor currency units. Never use `Math.random()` or wall-clock time inside deterministic transitions.
- Keep source database snapshots separate from career saves. Version imports and saves; validate before writing, preserve backups and reject unsupported versions safely.
- Keep money in safe integer GBP minor units for career-finance engine version 1. Debit wages and credit configured home-fixture income once through the accepted timeline; use the same financial rules for every club. Demo wages, contracts and budgets are original scenario values, not real-world facts. Renewals must enforce wage, term, budget and cash limits before any write.
- The 21 October user correction allows conditional agreed wage reductions. Preserve historical `RENEW_CONTRACT` replay; new offers use versioned `NEGOTIATE_CONTRACT`. Derive financial circumstances from actual state and age only from known birth dates. Do not invent demo ages or accept manager-declared eligibility. Guaranteed signing bonuses must debit cash once, count as spending, and leave one week's proposed wages affordable. Anchor concessions to the highest agreed wage to prevent compounded cuts.
- Preserve version-1 demo backups. Career-enabled demo version 2 adds a versioned financial replay boundary and mixed decision log, never trusted stored balances or ledger entries. Enabling an old demo starts at its current date without retroactive payments or income and does not reset football progress. Save financial and football decisions atomically.
- Use only appropriately sourced real identities in ordinary shipped data. Never guess current squads, invent player facts or import proprietary game ratings. Keep original game assessments separate from verified facts; unknown data stays unknown. Synthetic records belong in clearly labelled tests. The explicit development-only season demo may use generic demo clubs/players, with a persistent label, a separate save format/store, no fabricated source evidence, and no inclusion in the ordinary production build.
- Exhibition teams are temporary coach selections, not verified club rosters. Any uniform comparison baseline requires explicit opt-in, fills only missing ratings, preserves known editorial values and its assessment mode, and never changes source snapshots or career saves. Initial condition and morale are scenario inputs, not medical facts.
- Do not populate the current-season application with original, inferred or archival rosters as a substitute for verified current squads. Keep existing exhibition behavior and factual source snapshots unchanged. Record current-squad evidence, rights, access and blockers in `docs/data/CURRENT_SQUAD_SOURCES.md`; unknown facts remain unknown. Preserve career/exhibition compatibility and validate season binding before atomic calendar updates; derive table results from accepted match events.
- Derive match score, statistics and commentary from one authoritative event stream. Keep the initial config, accepted commands, seed and engine version replayable. Store exhibition sessions separately from careers; export each backup format explicitly.
- Keep hidden personality, development and potential data out of ordinary player-facing UI. Role scores must use documented weights and must not replace individual attributes.
- Keep gameplay local and credentials out of the client. Use semantic controls, visible keyboard focus, CSS Modules and shared design tokens.
- Preserve the current matte charcoal, navy gradient and silver skin, with Humanist 777 Black BT resolved locally. This newer presentation direction supersedes the original specification's green palette.
- Run `npm run check`, `npm test` and `npm run build` before calling a milestone complete. Match-engine changes also require the batch design-target report and browser match workflows. Add focused tests for domain or import behavior; report unverified platform claims honestly. Synthetic batch results are not empirical football calibration.
- Preserve existing user changes. Each cloud task already has an isolated checkout: use it and do not create a worktree unless the user explicitly requests one.
